# 产品重构验收记录

更新：2026-09-07。对照 main `66f67a6`，本轮开始时已有的工作保存在隔离证据目录的 `baseline/`，不将全部工作区差异归因于本轮。没有提交、推送或启动生产服务。Web 持续实测；iOS 原生验收单列，不以 Windows fixture 代替。

## 设计原则对应的实现

| 原则 | 当前落实 |
|---|---|
| 复用成熟成果 | Pi 会话、循环、skills 发现、原生文件/命令工具和参数校验；MCP SDK 的 stdio/Streamable HTTP；Radix UI；parse5 提取 HTML 正文；随技能保留社区来源与采用边界 |
| 简洁可扩展 | 删除重复文件工具、use_skill 别名、旧会话导入、旧 seed/schema 迁移、LibreChat 请求精简开关、过时 reset 与重复脚本；新安装与包更新采用内容哈希所有权 |
| 默认通用 agent | 统一对话入口，按任务加载 RP、小说、图片等技能；普通问答可直接插入，文件任务使用同一套 agent |
| 语义由 agent 判断 | 不用正则决定生图/编辑/合成、系列范围或是否退出角色；代码校验资源、参数、状态与审批。指定模型不可用时保留选择并报错 |
| 真实轨迹验收 | 历史来源、实际多轮、原始失败与修复回放分开；逐图视觉检查，真实浏览器操作。可复用的 HTTP 回放入口见 08 文档 |
| 用户掌握接入与提示词 | 自定义连接、协议、模型、工具与 prompts；原始 writing brief 字节校验；删除的预设不再自动复活，自定义或主动清空的 prompt 不被包更新覆盖 |

精简后仍保留必要的取消、恢复、审批和文件备份。媒体提交遇到结果不明时不自动再次付费提交；schema 不接受的参数、来源 ID 格式和超限来源在创建 job 前报错；实际文件与工作流约束在执行时继续检查。Windows 启动脚本解析可用 Node 24+，构建失败保留原服务。

真实图文交付补齐了通用文件工作流：`import_file` 按精确资料 ID 复制到工作目录，`publish_file` 把成果保存在本机资料库并返回可下载链接。它们复用上传入口的字节保存、去重和索引逻辑。离线 HTML 的内嵌图片不再当成正文索引；实际 36.5 MB 文件由 27,084 个错误文本块降为 3 个正文块，原文件字节保留。

Venice 原生编辑接口的画幅与生成接口分开声明，合并展示的模型也保留两套参数。真实请求曾因错误声明的 4:3 被提供方拒绝；修正后的契约会在创建 job 前拒绝这个编辑参数，不会静默换成其他画幅。依据见 [生成文档](03-generation.md)。

最后一轮参数审查还删除了 ComfyUI 忽略单边尺寸、取整指定 seed 和退回未声明方图的行为；编辑界面只提供执行时采用的参数。不支持的明确操作不会变成默认生图。实际隔离HTTP请求确认：文生图额外来源被400拒绝且没有job；单填512宽度留下明确失败job，未提交ComfyUI。合法尺寸到实际提交图的映射另由HTTP测试后端核对。

本轮没有把复杂姿势、长组图与严格RP的未通过项改成通过，也没有以服务端成功率代替效果。后续优化应保留这些病例，从实际上下文与结果判断原因。

进一步放大检查确认：100张场景里的第88张仍有人像雕塑，第94张和第100张有清楚可见的人。模型自报“只剩88不合格”不可信；5次替换预算已经用完，没有继续付费重试掩盖这个结果。RP的多模型对照也分别保留：有的将刚发生的交接改成数月前，有的维持交接但用英文回答中文请求。当前未发现这些失败对应丢失的用户输入或自动后端替换，尚不能用代码检查证明解决。

Grok最新两轮对照同样未通过：第1轮替站在门口的用户走到柜台，第2轮把双方上一场交出的钥匙说成昨天老顾客留下，Mira未识别矛盾。它对同一张三腿桥式图片的独立检查也错判“两条腿、没有不确定处”；实际原图再次打开确认有两条落地腿和一条抬起腿。证据为 `rp-grok-current/turn-1.json`、`turn-2.json` 与 `pose-visual-judge-grok-result.json`。这个结果不支持把默认模型改成Grok，也不支持宣称视觉自动验收已可靠。

随后补全4轮：Grok暂停后回答月相，没有角色或工具副作用，但指定两句话实际写了三句；回到故事又重复错误交接，并增加“上周”这个矛盾日期。为排除传递问题，隔离lab增加不保存原文的请求内容指纹：实际发送的前4轮用户文本、已读RP技能正文逐项哈希匹配，保留的writing brief也在请求中。视觉纠偏轮再次调用 `view_image`，发出的73,796字节JPEG与本地模型视图哈希相同，1248×832像素完整显示三只脚；模型仍错数两只。详见 `remaining-failures-transport-review.json`。这证明这些具体失败不能归因于遗漏技能、丢失本轮历史或把图片只作为文字ID发送；不等于证明所接模型具备可靠视觉推理能力。

GLM 5.3的两轮对照也未通过：第1轮没有要求的三个选项，第2轮改变交接、把唯一钥匙写成一串钥匙；Mira注意到“配好/修好”差异，却没有指出自己刚参与的交接与对方说法冲突。`rp-glm-current/turn-1.json`、`turn-2.json`记录原始输出；实际发给GLM的用户文本和已读技能正文同样通过哈希匹配。

## 按最新范围区分模型效果与产品缺口

2026-09-07 用户明确：在项目可控范围内做好，区分接入 API 的模型限制。上面的严格 RP、全范围复杂姿势和视觉自检失败继续保留为模型配置的效果用例，不再仅因它们失败，就把通用宿主实现全部判为未完成。实际用户文本、技能快照和图片像素的传递已有证据；这些具体失败未发现对应的输入丢失或后端替换。这是对所测配置和轨迹的归因，不是对提供方所有模型的能力断言，也不证明换一种有依据的提示或上下文组织永远无法改善。

短轮故事事实错误、完整清单漏项、复杂姿态生成错误和视觉模型误判，分别记录为写作/规划、生成、视觉理解问题。超长上下文的有效召回上限尚未系统测试，不能用短轮失败或 SDK 压缩通过代替。100张场景该次允许的5次替换已用完，没有追加付费调用。原生 iOS、跨版本升级与大规模性能边界仍需按项目责任单列；不能归为模型限制。新版相对 main 的完整审阅、此次发现并修复的问题及最终检查见 [11-main-review.md](11-main-review.md)。提交、推送、生产启动均未执行。
